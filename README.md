# Task Service API

Сервис для управления задачами с поддержкой периодических задач.

## Новая функциональность: периодические задачи

Добавлена возможность создавать задачи с настройками периодичности. Задачи автоматически "размножаются" на нужные даты при просмотре за период.

### Типы периодичности

- daily - каждые N дней. Пример: {"type":"daily","interval":2}
- monthly - каждый месяц в определенное число (1-31). Пример: {"type":"monthly","day_of_month":15}
- specific_dates - только на указанные даты. Пример: {"type":"specific_dates","dates":["2025-04-01","2025-04-15"]}
- parity - четные/нечетные дни месяца. Пример: {"type":"parity","parity":"even"}

---

### Архитектурное решение

Выбран подход "вычисление на лету" (on-the-fly):

- В БД хранится один шаблон задачи с правилом периодичности
- При запросе задач за период система вычисляет повторения динамически
- Дополнительные записи в БД не создаются

Почему не прегенерация:

- Прегенерация приводит к экспоненциальному росту БД (1 задача × 365 дней = 365 записей)
- Сложность редактирования (изменил правило -> нужно обновлять тысячи записей)
- Проблемы с производительностью при удалении

### Допущения и ограничения

1. Статус задачи - общий для всех вхождений периодической задачи
2. Рекомендуется ограничивать период запроса 90 днями для производительности
3. Граничные случаи:
   - 31-е число месяца автоматически пропускается в феврале, апреле и т.д.
   - Пустой список дат для specific_dates - задача не создается
   - Некорректный интервал для daily - используется значение по умолчанию (1)
4. Изменение правила периодичности применяется только к новым датам

  - recurrence_service.go - генерация дат по правилам

  - task.go - работа с БД

  - docs/ - Swagger документация

migrations/
  - SQL файлы миграций

---

### Принятые технические решения

1. Хранение правил в JSONB - гибкость для добавления новых типов периодичности без изменения схемы БД
2. Вычисление на лету - экономия места и простота редактирования
3. Валидация на уровне домена - метод Validate() в RecurrenceRule
4. Отдельный сервис для генерации дат - чистое разделение ответственности
